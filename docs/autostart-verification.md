## 7. 修正済み（初版のレビューで挙げた不整合と、その落とし所）

| # | 何が食い違っていたか | どちらを直したか |
|---|---|---|
| 1 | `install-autostart --dry-run` が「同じポートで手動起動しても2つ目は何も変えない」と言うのに、`cmdServe` は bind の前にトークンを読み・`--rotate-token` なら入れ替えていた（**負けた側が勝っている側の秘密を壊せた**） | **コード。** `cmdServe` を bind 先行にし、成功してからトークン取得 → `auth.setToken()` → `url.txt` の順にした。文面も「before it reads, rotates or writes anything … Only the log file records the refusal.」に書き換え。`test/cli.test.js` が実CLIで固定 |
| 2 | `rotate-token` が「every old cookie and bookmark is now rejected with 403」と断言した直後に「a server that is ALREADY RUNNING still holds the previous token」と書いていた（自己矛盾。コードは後者が正しい） | **文面。** 「replaced the token FILE. Nothing else changed yet:」の下に、再起動前は古い方が通り新しいURLが403、再起動後に逆転、と2項目で書き分けた。`--help` の1行説明も同趣旨に |
| 3 | `--help` が `live dashboard on http://127.0.0.1:47321` とポートを決め打ちしていた | **文面。** `http://127.0.0.1:<port> (default 47321; --port or CLAUDE_MONITOR_PORT)` |
| 4 | `url.txt` が `--persist-token` の有無に関わらず毎回書かれ、プロセスと共に死ぬURLが「入口に見えるファイル」として残っていた（しかも `rotate-token` がそこからポートを読んだ） | **コード。** 永続トークンのときだけ書く。永続化しない `serve` は `token: per-process (nothing stored; the URL dies with this process)` と出す。さらに `rotate-token` は token ファイルが隣に無い `url.txt` を残骸として無視する |
| 5 | `uninstall-autostart --dry-run` が、存在しない launcher にも `(would be removed)` と出していた | **コード。** `existsSync` の結果で書き分け。dry-run は `(would be removed)` / `(missing)`、実行時は `(removed)` / `(still present)` / `(missing)` |

同じ修正パスで併せて入った変更（初版のレビュー項目ではないが、7.2 / 7.3 の記述に反映済み）:

- `LogFile.rotate()` を `renameSync` 1回にし、**失敗しても truncate も削除もしない**ようにした。
  同じログに追記している別プロセスの行を捨てるより、一時的に上限を超える方が小さい失敗である。
  再試行は `retryRotateAtBytes`（もう1世代分育つまで待つ）で抑え、サイズは `open()` の
  `statSync` で読み直す。
- `maxBytes` を超える単一チャンクを `capChunk()` が UTF-8 境界で切り、
  `...[truncated N bytes]` を残すようにした。
- `assertQuotablePath()` を `vbsQuote` と `taskRunValue` で共有し、
  launcher パスの `"` / CR / LF を**登録前に**弾くようにした。
- `printWithToken()` がログ（同期 `fs`）を先に、コンソール（Windows のパイプでは非同期）を
  後に書くようにした。ここで殺されても永続する記録の方は残る。
- `cli.js` が `parseArgs` / `boolFlag` / `pathFlag` を export し、`main()` は
  直接実行されたときだけ走るようにした。これで `test/cli.test.js` が
  関数単位のテストと実プロセスの spawn を同じファイルに置ける。

**軽微な不整合（修正済み、2026-09-04）。**
`install-autostart` / `uninstall-autostart` は `--dry-run` を付けていない実行でも
コマンド行を `would run : …` と表示していた（その下に実際の終了コードを出す）。
非 dry-run では `ran :` / `wrote :` に切り替えるよう src/cli.js を修正した。
dry-run の出力は変わらない。テスト 525 件 pass のまま。

### 8.3 起動方法の比較（`cli.js tray` が wscript を経由する理由）

トレイホストを node の子として直接起動できるか測った。判定は「launcher が終了した
8秒後に `tray.pid` が在り、その PID が生きているか」。

| 起動方法 | 結果 |
|---|---|
| `spawn(powershell, {detached: true, stdio:'ignore', windowsHide: true})` | **`tray.pid` すら書かれない。** `detached` は Windows では `DETACHED_PROCESS`。コンソールを一切持てず、PowerShell 5.1 はホストを初期化できずに1行も実行せず死ぬ |
| `spawn(powershell, {detached: true, windowsHide: false})` | 同上 |
| `spawn(powershell, {stdio:'ignore', windowsHide: true})`（親が生きている間） | 起動する。ただし**親の node が終了した瞬間に道連れ**になる（サーバの node だけが孤児として残る） |
| `wscript.exe <launcher.vbs>` → `sh.Run cmd, 0, False` | **両方とも8秒後に生存。** 失う親が居ない |

よって `cli.js tray` は 7.3 と同じ `.vbs` を書いて wscript に渡し、
wscript が終了した時点で launcher を消す（`sh.Run` は wscript が終わる前に実行済み）。

### 8.10 レビュー指摘とその処理（2026-09-04 第2版）

トレイ常駐の初版に対するレビュー（「このままでは登録して良くない」）。8件すべてコードで
確認してから対応した。**「そういう仕様です」で流したものは無い。**

| # | 指摘 | 確認結果 | 対応 |
|---|---|---|---|
| 1 | **PID 再利用。** `alivePids` / `killTree` が裸の PID を信じる | **本物。** `tray.pid` に `startedAt` は在ったが検証に使っていなかった。番号が使い回されていれば `autostart-status` は他人のプロセスを「running」と呼び、`tray-stop` は `taskkill /T /F` でそれを子ごと殺す | `.ps1` が各 PID の**プロセス名と開始時刻**を記録するようにした。`probeProcesses()` が `Get-Process` から名前と開始時刻を取り、`pidMatches()` が 60 秒の許容差（`src/sessions.js` と同じ）と名前で突き合わせる。`killTree()` は `expect` を**必須**にし、直前に再検証して食い違えば**何も実行しない**。状態は `stale tray.pid (pid N reused by chrome)` と書き分ける |
| 2 | **Mutex に負けた側が勝った側の `tray.pid` を消す** | **本物で、これが一番痛い。** `$script:PidFile` を Mutex 取得**前**に代入していたため、負けて `exit 0` する経路でも finally の `Remove-PidFile` が動き、**生きているインスタンスのファイルを消して**いた。以後 `tray-stop` は「止めるものが無い」と言い、アイコンは生きたまま到達不能になる | `$script:PidFile` は Mutex を**取れてから**代入する。`Remove-PidFile` は（a）Mutex 保持時のみ動き、（b）ファイルの `trayPid` が自分の `$PID` のときだけ消す。負けた側はログに1行残して去る。`tray-stop` は `tray.pid` が無くても**まず名前付きイベントを送ってみる**ようにした（コストはゼロで、失われた pid ファイルの分を拾える） |
| 3 | **`Open-Dashboard` の URL 検査が `^https?://` だけ** | **本物。** `url.txt` を書ける者が任意の URL をシェルに渡せた | `server.js` `openBrowser()` と**同じ**許可リスト `^http://127\.0\.0\.1:\d{1,5}/\?t=[0-9a-f]{64}$` を当てる（`-cmatch`＝大小区別。JS 側にも `i` は無い）。弾いたら素の loopback URL に落とし、ログには**ファイル名だけ**を `url.txt rejected` として残す |
| 4 | **`tray.pid` の書き込みが非アトミック** | **本物。** 書き込み途中を読むと JSON が半分になる。`readTrayPid()` は落ちないが「トレイ無し」という**間違った答え**を返す | `tray.pid.tmp` に書いて `File.Replace`（Win32 `ReplaceFile`）で差し替える。overwrite 付き `File.Move` は **.NET Framework 4.x に無い**（.NET Core 3.0 で追加）ので PS 5.1 ではこれが唯一のアトミック手段。`Replace` は対象の存在を要求するので初回だけ `Move` |
| 5 | **`ConvertTo-QuotedArg` が末尾バックスラッシュを拒否しない** | **本物**（ただし現状 `noTrailingSep` が手前で落としているので到達しない） | 末尾 `\` を明確なメッセージで拒否。多層防御として残す |
| 6 | **リポジトリを移動すると黙って死ぬ** | **本物で、しかも検出経路が1つも無かった。** `.vbs` は動き、`sh.Run` は wait=False なので失敗を報告できず、wscript は 0 で終わり、トレイホストは読み込まれないので**自分が動かなかったことをログに書けない**。タスクは「成功」。症状は「アイコンが出ない」だけで、オーバーフローに隠れているのと区別が付かない | `install-autostart` が launcher の隣に `autostart.json`（sidecar）を書き、`uninstall-autostart` が消す。`autostart-status` がそれを読んで `trayScript` / `node` / `cli` / `launcher` の実在を確かめ、欠けていれば `*** LAUNCHER POINTS AT A MISSING FILE ***` と理由を出す。sidecar が無い環境では「ok」でも「壊れている」でもなく**「この検査は使えない」**と言う。`.vbs` の読み返しは採らなかった（自分で生成した文字列から2つの形に分けてパスを復元することになる） |
| 7 | **Mutex が `Local\`（ログオンセッション単位）** | **仕様として妥当。変更せず、説明を足した。** `Global\` にすると2人目のトレイが**黙って**起動を拒否し、アイコンも理由も出ない。現状は2人目もトレイが起動し、サーバが bind に負けて**そのセッションのアイコンが赤くなる**。1人目は無傷 | `.ps1` にコメント、architecture 7.5 と 7.4-12、README に明記 |
| 8 | **`autostart-status` が `?t=` 付きURLを全文表示する** | **本物。** これは不具合報告に貼り付けられる出力である | 既定で `?t=<redacted>` に伏せ、`--show-url` で全文。`serve` は従来どおり1回だけ全文を出す（それがあの行の存在理由なので） |

**この対応中にさらに1件、実測で見つけて直した。** `File.Replace` の backup 引数に
`$null` を渡していたところ、PowerShell が `$null` を**空文字列**に変換するため
「パスの形式が無効です」で毎回失敗していた。catch が握り潰していたので**静かに**壊れ、
`tray.pid` は初回の書き込み（`Move` 経路）のまま **`serverPid` を永久に `null`** に保っていた。
`[NullString]::Value` を渡すのが正しい。スモークで `server pid : (not yet)` が
消えないことに気付いて発覚した —— 指摘 4 の修正が、指摘 1 の修正を無効化しかけていた。

## 9. 実登録の失敗と XML への切り替え（2026-09-04 第3版）

**第6章「未確認」の筆頭 ——「`schtasks /Create` が実際に成功するか」—— の答えが出た。
成功しない。** 実測（この環境、非昇格）:

```
> schtasks /Create /TN X /TR "cmd.exe /c exit" /SC ONLOGON /RL LIMITED /F
エラー: アクセスが拒否されました。
（終了コード 1）
```

初版から `/SC ONLOGON` で組み立てていた argv は、**この環境では一度も通らなかった**。
理由は権限の問題ではあるが、単に「管理者で実行せよ」ではない ——
`/SC ONLOGON` は**ユーザーの紐付かない**ログオントリガー、すなわち
**全ユーザーのログオンで発火する**タスクを作る。それは管理者の行為である。
そして schtasks のコマンドラインには、これを1ユーザーに絞る手段が無い。
`/RU` は「何者として実行するか」であって「誰のログオンで起動するか」ではない。

同じ環境で、XML 形式は**通った**:

```
> schtasks /Create /TN X /XML task.xml /F
成功: スケジュール タスク "X" は正常に作成されました。
（終了コード 0、状態 準備完了、ログオン モード 対話型のみ。/Delete も成功）
```

`<LogonTrigger>` の中の `<UserId>DOMAIN\user</UserId>` 1個が分かれ目である。

### 9.1 変更点

`installAutostart` は `<monitorDir>\autostart.xml` を **UTF-16LE + BOM**（宣言も
`encoding="UTF-16"`）で書き、`schtasks /Create /TN claude-monitor /XML <path> /F` を実行する。
XML は登録後も残す（`autostart-status` が見せる）。`uninstall-autostart` が
`.vbs` / `.json` と一緒に消す。

生成される XML（`--dry-run` が全文を印字する）:

```xml
<?xml version="1.0" encoding="UTF-16"?>
<Task version="1.2" xmlns="http://schemas.microsoft.com/windows/2004/02/mit/task">
  <RegistrationInfo>
    <Description>claude-monitor tray host (installed by `node src/cli.js install-autostart`)</Description>
  </RegistrationInfo>
  <Triggers>
    <LogonTrigger>
      <Enabled>true</Enabled>
      <UserId>MYPC\alice</UserId>
      <Delay>PT10S</Delay>
    </LogonTrigger>
  </Triggers>
  <Principals>
    <Principal id="Author">
      <UserId>S-1-5-21-<redacted>-1001</UserId>

      <RunLevel>LeastPrivilege</RunLevel>

**`<ExecutionTimeLimit>PT0S</ExecutionTimeLimit>` が一番効く。** 既定は 72 時間で、

`autostart-status` はこの値を読んで、`PT0S` 以外なら警告を出すようにした。

```

### 9.3 この作業で見つけた別の不具合

**`whoami` が Git の MSYS 版に食われる。** SID は `whoami /user /fo csv /nh` の2列目から
取るが、`whoami` を裸の名前で spawn すると、PATH に Git for Windows の `usr\bin` が
先に入っているシェルから実行したとき**そちらの `whoami`** が拾われる。
MSYS 版は `/user` を理解せず `whoami: extra operand '/user'` で終了コード1になる:

```
whoami      -> status 1, out ""
whoami.exe  -> status 1, out ""   stderr: whoami: extra operand '/user'
```

catch とフォールバックが効いていたので**静かに**アカウント名に落ちていた（動きはする）。
`%SystemRoot%\System32\whoami.exe` を絶対パスで呼ぶよう修正し、SID が取れるようになった。

**テストが実 `~/.claude-monitor` に書き込みうる形になっていた。** `autostart.xml` と
`autostart.json` の既定パスを `monitorDir()` 基準にしていたため、
launcher を一時ディレクトリに向けた `installAutostart({launcher: <tmp>})`（テストの常套手段）が
**XML と sidecar だけ実ディレクトリに書く**状態になっていた。
3つのファイルは1組なので、既定を**launcher と同じディレクトリ**に変更した。
`npm test` 後に実 `~/.claude-monitor` を確認し、`autostart.xml` / `autostart.json` が
作られていないことを確かめてある。
